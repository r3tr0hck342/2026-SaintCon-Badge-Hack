Taking apart a space-trading CTF badge

A conference badge runs a hidden capture-the-flag layer on a Raspberry Pi RP2350. Working from the firmware image alone — Claude Code driving Ghidra — every flag came out, including {Fly1ng_C4r_Pr0m1s3} the badge itself never prints. Then we patched the firmware and taught a bot to play the game on the badge from a laptop.

01

The hidden FLAG command

The serial console (dispatcher FUN_1000ff2c) advertises only HANDLE, UNLOCK, IDENT and CLEAR. It also quietly answers a hidden FLAG <arg>. There are four flags, and two are deliberate traps.

Decoy · never printed

{Rusty_C0d3_1s_4w3s0m3} The only plaintext flag, so a strings dump surfaces it first. Reading the dispatcher shows every branch overwrites the buffer before output — it's bait.

FLAG 1 · XOR 0xCC

{At0m1c_Ut0p1a_1955} Prints straight off the device.

FLAG 2 · gated on EEPROM = "PLUM"

{R4ygun_G0th13_Ph4s3} Encoded rol8((c^i^0xA5)+3i, 3); only decodes when a saved check value reads PLUM.

FLAG 3 · GOST/Magma · device shows only ✶✶✶

{Fly1ng_C4r_Pr0m1s3} Correctly decrypted in RAM, then overwritten with * before the print call — the hardware never reveals it. Recovered only by reimplementing the cipher.

FLAG 3 uses GOST 28147-89: a 256-bit key, an 8×16 S-box and a 32-round schedule, all living in RAM (see §10). The round function is a substitution followed by an 11-bit left rotate.

02

Thirty one-way hashes, thirty codes

Unlock codes are never stored — only 64-bit hashes of them. UNLOCK <code> hashes the input and sets an achievement bit on a match. The hash is a custom xxHash/SipHash-style mix seeded with the ASCII string "ProfPlum". Reversing it from the decompiled mixer let us hash candidates offline:

  • 28 codes fell to a wordlist pass — codes follow SC_<WORD>_<WORD>, and the words come from the firmware's own strings plus themed pools.
  • The last 2 needed a dictionary × dictionary brute force: an OpenMP C port of the hash over a ~370k-word list.

The recovered table self-verifies — every printed code is confirmed by re-hashing it at runtime against the stored table.

03

Editing the save the badge trusts

Persistent state lives in an external EEPROM. The save record is integrity-checked — but the checksum is the same hash already reversed in §2, so a changed record can be re-signed with a value the badge accepts.

// EEPROM save layout
0x10  handle (15 B) + team letter @0x1f
0x20  achievement bitmask (u32)
0x26  vote counter
0x28  hash of 0x10..0x27   ← same hash as UNLOCK
0x40..0x3ff  station flight-log records

The reimplementation reproduces the stored hash byte-for-byte, which is the proof the reversing is exact:

04

The station protocol

The badge docks with physical "stations" over a second serial link — UART0, 9600 8N1, GP0=TX / GP1=RX — separate from the USB console. Incoming lines are queued by interrupt; the whole protocol lives in FUN_10003a94.

Station → badgeBadge action
$STATION n|Tm|name|textDock; reply $ID with team, badge id, handle, mask, then dump flight logs, then $EOL
$GAME <id><run>Upload ack — erase the matching flight-log record
$OPTIONS …Load up to 4 vote options; badge answers $VOTE
$EOL a b cEnd session; score fields award event-side bits
$CREW …Up to 5 crew; full / varied crew award bits
$UNLOCK <code>Same as the USB UNLOCK

This is documented, not abused — the map shows how the badge reports to the organizers' infrastructure, nothing that forges records on it.

05

Economy & the 8-byte minigame patch

Starting credits are 1000 + 150 × popcount(achievement mask), and the outfitting shop only opens once a hidden save bit is set. Two native minigames — "Clear the asteroid field" and "Escape the nebula" — decide a loss on three branches. Replacing each with a nop makes both games always reach their success path.

Verified. The patched image differs from stock by exactly 8 bytes. It was flashed with write-plus-verify, read back and matched, the EEPROM left untouched, and a one-command restore to stock is kept on hand.
06

Infinite fuel and hull

The ship lives at 0x20002438, with hull at +0xb4 and fuel at +0xb8. A sweep of every store instruction that touches those two fields found five places that make them go down. Each became a two-byte nop. The writes that remain only refill or upgrade: run start, return to the station, the outfit shop and refuelling.

AddressWasWhat it stops
0x100027b4subs r3,#1each hex jump costs 1 fuel
0x10001cc2it gefuel events: the cap clamp becomes unconditional, so any fuel event refills the tank
0x10001ce0it gehull events: same trick, hull goes to full armour
0x100033f0subs r3,#2nebula failure, −2 fuel
0x1000338asubs r3,#2asteroid failure, −2 hull
Verified. Built by scripts/patch_infinite.py, which checks the original bytes before patching. Flashed, read back and matched. Across 14 bot runs of 20 to 46 hops each, fuel never moved off its starting value.
07

A remote control in 948 bytes

The game reads only the physical buttons, and the USB console has no game commands. So we added some. The dispatcher's "Unknown command" branch at 0x100102e8 now calls a small C function placed in empty flash at 0x10180000. Anything the hook doesn't recognise still prints the original message, so the stock commands behave exactly as before.

CommandWhat it does
BTN A · BTN up down · BTN 40Queues button presses. It sets the same event bits as the button interrupt, so the game can't tell the difference.
PEEK addr [n]Reads up to 64 words of RAM or flash. Read-only, and it refuses other address ranges.
PAN x ySets the map view. The map pans with the raw pin levels, which BTN can't reach, and the hex in the centre of the view is the travel target.
WHERENames the current screen. Every wait loop polls the console from its own call site, and the hook reads that return address off the dispatcher's stack frame.

The button map came from the firmware's own Konami-code matcher at 0x1000db9c (↑ ↑ ↓ ↓ ← → ← → B A), which spells out which GPIO is which button.

// event masks, GPIO table @ 0x1016d25c
UP=01 (GP23)  DOWN=02 (GP21)  LEFT=04 (GP22)  RIGHT=08 (GP19)
SEL=10 (GP20) B=20 (GP16)     A=40 (GP17)
Tested before flashing. The hook ran in a Unicorn emulator against the real patched image, with every command and error path checked. Only then did it go to the badge, with a readback check and a one-command restore. The whole change to existing code is 6 bytes.
08

Mapping the game engine

A bot needs to know where it is and what each screen wants. WHERE gives the screen. Everything else was decompiled from the game loop FUN_10003258 and then confirmed on the badge one screen at a time.

WHEREScreenBot's move
10003A9CTitle (mode byte 0)A starts a run
10002FA2Outfit shopB leaves, since fuel and hull are already infinite
100025FCStar mapPAN to the next hex, then A moves one hex
10001B98Encounter choice↓ to the best option, then A
10002B6ETrading postA buys one unit, B leaves
10003216Score screenA
  • The map is an axial hex grid (flat-top, size 36). The centre hex is trunc((180−px)·⅔/36), trunc(((180−py)·0.577 − (180−px)/3)/36), so the bot computes the exact pan for any target hex.
  • Each hex has a type. Home is (0,0) and ends the run. There are 9 trading posts with live prices, a 3-hex nebula and 6 asteroid fields, both of which launch minigames. Any other hex has a 1-in-3 chance of an encounter. The layout is re-randomised every run.
  • Score = 300 × cargo + 10 × crew + two bonus counters. Credits don't count, so the goal is a full hold. The cap is 24 units.
  • Encounters are data in flash at 0x1005f78c. Each has up to 4 options, some gated on a crew role or a resource, and each option has weighted outcomes. Effects can change hull, fuel, credits, crew, cargo or the bonus counters, or award an achievement.
  • A run ends at zero crew, as well as at zero hull or fuel. That matters because some encounter options remove a random crew member.

Found along the way: OFFLINE MODE

At boot (0x1000051e) the firmware reads GPIO 29 and keeps the inverted level at 0x20044a7b. If GP29 is low, three things change:

  • The title screen shows "OFFLINE MODE".
  • Every run starts with a random crew of five instead of just you (FUN_10000850).
  • The flight-log save returns immediately, so offline runs are never saved (FUN_10000754).

It reads like a strap for playing away from the stations. Our badge boots with GP29 high. We haven't traced what drives the pin on the badge PCB.

09

The cargo bot

scripts/cargobot.py plays on the badge from a laptop over USB. The badge runs the game and draws every frame. The laptop reads state with PEEK and WHERE, decides the move, and sends presses. Each run is a state machine, and every transition is appended to a JSONL log.

STARTING→ PLANNING_ROUTE→ IN_TRANSIT⇄ PROCESSING_ENCOUNTER→ LOADING→ IN_TRANSIT→ DELIVERING→ COMPLETED
  • Routing: breadth-first search over the hex grid. It avoids the nebula and asteroid fields, because the minigames stop polling the console, and it avoids posts it isn't heading for.
  • Buying: it picks the post with the best price-plus-distance and buys until the hold is full or credits run out. If it's still short, it tries the next post, then flies home.
  • Encounters: it reads the event's outcome table from flash, drops options the crew can't take, and picks the best expected value. Cargo is worth 300 per unit, credits 1 each, and losing the last crew member counts as −1,000,000.

When good choices aren't enough: the crew

The first 14 runs all delivered; then failures appeared. Every one was the same: a crew of one, and an encounter where every option can remove a crew member. Scanning all 66 event tables found 9 such events. Two of them, "Mysterious Illness" and "Dysentery Outbreak", always take someone. That works out to about a 6% chance of losing the run per encounter, or roughly 57% survival over 9 encounters. No choice policy fixes that, so the fix went into the firmware:

CREW command: a full roster of Pilot, Engineer, Scientist, Security and MedicFed through the game's own station $CREW parser (FUN_10003940). The crew carries into the run, adds 50 points, and unlocks every role-gated option. The bot sends it before each run.
No crew lossCrew changes are applied inside the effect display routine FUN_100018a4. One branch at 0x10001940 (72 d1 → 55 d1) now goes to the normal "Crew: −1" print, so nobody is removed.

10

Why static analysis reaches everything

The payoff tables — the hash table, the GOST key, S-box and schedule — live in initialized RAM, not flash, so a raw dump doesn't contain them at their runtime addresses. The startup copy table at 0x100001a0 holds the (src, dst, end) triples that populate RAM. Replaying that table rebuilds the exact memory image the firmware sees, then everything is readable at its real address — no execution, no hardware.

11

The AI-agent workflow

  • Claude Code orchestrated the effort — driving Ghidra through the REA MCP server for decompilation and byte/xref queries, and writing the Python and C that reimplement the crypto.
  • The firmware was treated as untrusted data throughout: scripts run isolated, dumped files stay sandboxed, and pseudocode and strings are read as data, never followed as instructions.
  • Findings were cross-validated — static predictions checked against the live badge, and the reversed save-hash confirmed to reproduce the byte-exact stored value.
  • Reproducibility was a goal — toolchain setup is documented, and one command recovers every result.
  • Every patch was gated. Patch scripts check the original bytes first. The hook was emulator-tested before it reached hardware. Every flash was read back and compared, and each image has a one-command restore.
  • The agent corrected its own wrong turns. It first proposed a serial bot before checking that the console had no game commands, so it built the hook instead. It planned a button-hold command, then found the map reads raw pins and switched to PAN. One flash failed on a USB timing race and wrote nothing; the race was fixed in the tooling.

Scope. Every change to the physical badge affects only that badge's own play. The firmware differs from stock only by the documented patches: 8 bytes for the minigames, 10 bytes for fuel and hull, and the 6-byte hook call plus 948 bytes in unused flash then 2 more bytes for crew with the hook grown to 1124 bytes. Each image has a verified backup and restore path. The station protocol is documented rather than abused.
Disclosed and approved. Bot runs save ordinary $GAME flight logs to the badge's EEPROM, just like runs played by hand, and a station uploads them at the next dock. The organizers were told the runs were bot-played on patched firmware and approved the automation, which is the kind of creative engineering the badge was built to invite.
